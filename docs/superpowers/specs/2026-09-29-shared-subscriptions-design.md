## 1. 背景

第一步把订阅处理搬到了 worker 级，但键带连接：同一查询在 worker 里仍有 N 个订阅对象，每条通知各自
ZRANGE、解码、求集合差。

Linux 实测（2000 个真实 ws 连接，每人订最近 1024 条聊天；第一步设计稿 §12.2、
`benchmark/sub_scenarios_result.md`）：
- 一个 worker 约 1 条/秒就打满，每条消息每个连接 450~550µs；
- tick 屏障让轻负载时所有连接等整批算完，推送 p50 从 629ms 升到 904ms；
- 堆 3~5GB（2000 × 1024 个行订阅对象），全量 GC 一次 0.5~1.7 秒。

共享之后，每条消息每个连接只剩暂存、交付、编码（实测每帧 2.2µs）、发送，估算 30~60µs，单 worker 约
10 条/秒量级；堆里也不再有成百万个行订阅对象。

## 2. 目标与非目标

目标：
- 非 RLS 组件的订阅，以及 admin 的订阅，按查询在 worker 内只有一个订阅对象，订了同一查询的连接都是它的
  成员。每条通知的读与比对在 worker 内只做一次。
- 后加入的连接用共享订阅的快照做回复，不读库、不补读。
- 回复排在之后的推送前面，快照与之后的推送衔接得上（§3.3、§4）。
- 共享订阅的初始读出错时有限重试（用户已定），顺带解决"首次读落到死副本，新订阅就失败"（第一步设计稿
  §4.9 末尾）。

非目标：
- RLS 订阅共享：按连接私有（第一步已定）；
- 跨 worker 共享；
- 多个连接共用推送编码：实测每帧 2.2µs，不值得；
- 最后一个成员离开后的保留期。

## 3. 设计

### 3.1 共享键

`(类别, 表, 查询, 可见性)`：
- **类别**：get / range / table。
- **表**：`(comp_cls, instance_name, cluster_id)`。不直接用 `TableReference`：`Table` 多一个 backend 字段，
  与同地址的 `TableReference` 互不相等。hub 本来就按 backend 分，不用再区分。
- **查询**：
  - get：row_id；
  - range：`(index_name, repr(left), repr(right), repr(limit), bool(desc))`，limit 在前半段校验为整数
    （`BackendClient.check_range_`）；
  - table：行数上限（`max_table_rows`）。订阅按建它的连接的上限读初始行、做 RESYNC；服务器里各连接的上限都是
    `MAX_TABLE_SUBSCRIPTION_ROWS`，照样共享。

  不用 sub_id 字符串做键：`right=None` 与字符串 `"None"` 拼出同一个 sub_id，共享后会让别人拿到另一个查询
  的结果。`repr` 在 None / bool / int / float / str 之间不会撞；`1` 与 `1.0` 分成两个键，只是少共享一些。
  `desc` 按 bool 规范化（客户端传 1 或 True 是一样的，sub_id 也按真假拼）。反过来，同键一定同 sub_id：
  limit 若按 `int` 规范化，同一个连接用 `10` 与 `10.0` 两个 sub_id 会加入同一个订阅，成员表按连接记就乱了。
  sub_id 仍按 `make_query_id_` 给客户端，记在各成员上（SDK 的 `MakeSubId` 在预测它，格式不能动）。
- **可见性**：订阅的 `rls_ctx` 为 None（组件不是 RLS，或 ctx 是 admin）时可以共享；否则私有。

hub 新增共享登记表 `_shared: dict[键, 订阅]`，私有订阅不进表。订阅关闭时（最后一个成员离开、初始化失败、
结果为空）同步从表里撤掉，前提是表里登记的还是它。

### 3.2 快照：成员手里的状态

可共享的订阅维护一份快照 `snapshot: dict[row_id, 行]`，也就是"成员的客户端手里现在有什么"：
- 初始化完成时，由初始读的可见行填上；
- 之后 hub 在 `_stage` 暂存更新时顺手改它（行为 None 就删）。在暂存时改、而不是交付时改：tick 中途加入的
  新成员拿到的快照已经含这次更新。
- 暂存按订阅：一个 tick 里同一订阅的更新合并成一份 dict（后到的覆盖先到的），tick 末尾交给**交付那一刻**
  的成员，成员们共用这一份（只读），待发区里还有上次没取走的才拷一份合并。不按成员各拷一份：成员成百上千
  时，每个变动的频道都要走一遍成员表（§10 第 13 条）。
  - tick 中途退订的不给；退订后又重订的按重订算，退订前暂存的不会交给新的它（§10 第 1 条）。
  - tick 中途加入、加入时订阅已有暂存的，hub 记下加入那一刻的暂存（拷贝），交付时只给它之后变了的（行对象
    每次更新都是新读出来的，按对象认）。它的快照已含加入时已暂存的。
- 快照按回复顺序排好的列表缓存到下次变动（`_stage`、就绪、`_rerange` 改了顺序），后加入者共用：整表订阅的
  快照可能有十万行，每个后加入者重排一遍太贵（§10 第 15 条）。
- 快照放在 hub 层、按暂存的更新维护，不碰三种订阅的比对逻辑。私有订阅不维护：没人会加入，每人一份背包
  的行对象也不是小数。
- 范围订阅的回复要按索引顺序：`IndexSubscription` 记下最近一次 ZRANGE 的 id 顺序（初始读、`_rerange`
  都拿得到），快照按它输出。只改非索引字段的更新不影响顺序。
- 整表订阅的快照就是整张表的可见行，最多 `MAX_TABLE_SUBSCRIPTION_ROWS` 行，每个 worker 一份。今天是每个
  连接一份 `known_ids`，每次订阅还要全量读一遍；共享后，后来的连接当场拿快照。
- 行对象不拷贝：暂存、快照、各成员的待发区和回复引用的是同一个 dict，之后都不再改它（每次更新都是新读
  出来的新 dict）。

### 3.3 订阅流程：统一走占位（用户已定）

get / range / table 三种订阅都拆成两段（今天只有整表订阅这样做）：

- **前半段**（在接收协程里）：权限检查、算 sub_id、同连接的重复订阅、找或建共享订阅、登记成员、计入订阅
  数。只有按非 id 索引的 `subscribe_get` 要先查一次索引拿到 row_id（它决定共享哪个订阅），这一次短读仍在
  前半段，同今天；其余的读、SUBSCRIBE、等共享订阅就绪都在后半段。
- **后半段**（后台任务，结果填进 push_queue 里的占位，同今天的整表订阅）：等订阅就绪，返回快照。

接收协程登记完就去处理下一条消息，不再等订阅的初始读。登录时连发的几个订阅也因此并发进行。

成员在前半段就登记进订阅的成员表，这是安全的：
- **回复在推送前面**：`sub_call` 先把占位放进 push_queue、再做前半段登记（§10 第 12 条），发送循环按队列
  顺序发，之后交给这个成员的推送都排在回复后面。push_queue 满（1024 条没发出去）时放占位要等，这期间还没
  登记，推送协程插不到占位前面。前半段出错时占位作废，连接随即断开。
- **就绪前登记的成员**：初始化期间订阅不产生任何更新（行 / 范围订阅还没生效，整表订阅只攒 pending）。
  它们的回复是**就绪那一刻**的快照：初始化结束时把快照一次交给当时等着的各成员（每个成员一个 future），
  之后的更新它们都收得到，两边衔接得上。
- **就绪后登记的成员**：前半段当场同步取快照，之后的更新都收得到。

门面每次登记发一个新记号（`_regs`），后半段、重复订阅都按它认 sub_id 还是不是自己那次登记：退订后同一连接
重订同一查询，会重新加入同一个共享订阅对象，按对象认不出来（§10 第 7 条）。

订阅数在前半段登记时就计入 `count()`，其中可能有随后不成立的（force=False 的空结果、不存在或不可见的行，
它们会自己撤掉）。`sub_call` 到了上限时先等在途的后半段都有结果（这期间不接收新消息），再按成立的判，同
dev 逐条处理的语义；离上限远时不等（§10 第 4 条）。

### 3.4 共享订阅的初始化

第一个成员建订阅（订阅对象这时就建好，状态为空），初始化在 hub 自己的任务里跑，不挂在任何连接上：
- **行订阅**：attach（占位、订阅频道）→ 读行 → 记指纹、快照 → 生效。
- **范围订阅**：读 range 拿到初始行 → 填状态（`last_range_result`、各行指纹、id 顺序）→ attach → 生效。
- **整表订阅**：attach（立即生效，攒 pending）→ 隔 T 全量读 → `finish_init_`，同今天。

行 / 范围订阅在初始化期间**不生效**（tick 跳过它们）；生效时对全部频道定向补读一次（今天 `subscribe_get`
/ `subscribe_range` 本来也补读全部频道）。生效前被跳过的通知，补读时刻都晚于它们。这样一来，读的期间就
不会有推送抢到回复前面，`subscribe_get` 的 `UNKNOWN` 处理不再需要，删掉。私有订阅也走同一套初始化，
只有一条代码路径。

初始化的结果：
- 交给等着的成员做回复：共享订阅给就绪时的快照；私有订阅不维护快照，给初始读到的、按它的 ctx 可见的行
  （同今天）。
- get 的行不存在、整表超过行数上限：订阅不成立，当场撤掉共享登记（之后同一查询新建），等着的成员都回
  None、各自退订（退订等 UNSUBSCRIBE 回来才返回，同今天）。就绪后加入的：get 的行已经不在了（快照为
  空，先重读确认，§3.6）、整表已超过它自己的上限，同样回 None、不加入。
- 范围订阅没有行时照样建；`force` 由各成员自己判断（§3.6）。

出错（用户已定：有限重试后失败）：
- 初始读出错时换一个随机副本，按 1、2、4 个 interval 退避重试，共 `INIT_RETRIES` 次（默认 3，约 0.7 秒）；
  还不行，才让等着的成员失败：后半段抛出 → 发送循环记日志、断开连接，同今天。
- attach（SUBSCRIBE）出错同样重试。后端调用里漏出来的 CancelledError（初始化任务并没有被取消）也当作出错。
- range 的查询参数（limit 是整数、索引存在、边界合法）在前半段校验，不合法当场断开，不登记、不读库：不能
  让它在后台读了、重试了约 0.7 秒才失败（§10 第 6 条）。
- 初始化期间成员全走了（连接断开、客户端 unsub）：取消初始化任务，撤掉占位。
- 初始化任务不论怎么结束，等着的成员都有交代：成员撤空、hub 关闭时已经交代过；别的 BaseException（事件循环
  关闭时的取消等）让等着的成员拿到 ConnectionError、撤掉共享登记（§10 第 5 条）。
- 已有结果的订阅（就绪、不成立、已关闭）再来等的当场回，hub 已关闭的抛 ConnectionError（§10 第 8 条）。
- 处理循环意外结束后，新建和加入共享订阅都会把它拉起（§10 第 9 条）。

### 3.5 离开

成员退订或连接关闭时，撤掉它的成员身份。成员撤空就关闭订阅、从共享登记表撤掉、退订没人要的频道，同第
一步。不设保留期。

### 3.6 回复的细节

- **range 的 `force=False`**：快照为空时这个成员不加入（撤掉成员身份），回 (None, [])，同今天。
- **回"没有"之前先重读**（§10 第 3 条）：快照落后于提交至少一个 interval（通知隔一个 interval 才读），成员的
  推送全都卡着时一直不动。据它回"没有"的话，连接就不是成员了，随后推来的行它再也收不到。所以加入别人建的
  共享订阅、或重复订阅共享订阅时，get 的快照为空、force=False 的范围为空，先等订阅重读一次判定频道（行订阅
  是行频道，范围订阅是索引频道，`recheck_channel_`），再按那之后的快照判：hub 定向补读它，在请求之后才开始
  的 tick 里重读到了，就把那时的快照交给等着的成员（`SubscriptionHub.recheck_`），与 dev 订阅时读库一样新；
  有成员在等时订阅不算卡住（§3.7）。自己新建的订阅不用：初始读就是为这次订阅读的。代价是这几种回复晚
  1~2 个 interval。整表订阅超过行数上限仍按快照判：快照就是这个连接会拿到的行。
- **同一连接的重复订阅**（sub_id 已登记）：共享订阅回快照，不读库；私有订阅没有快照，先等已有订阅的初始化
  （它不成立就回 None，§10 第 2 条），再重读，读完确认登记还在。get 的行现在不可见 / 已删除、整表超过上限
  时撤掉旧订阅，同今天。
- 重复订阅的回复变成"订阅已推给客户端的内容"（今天是重新读的、可能落后的一份），docstring 与 SDK 注释
  跟着改。

### 3.7 背压与共享

第一步的背压（成员的推送全都卡着时订阅先不读、攒着通知，成员取走待发区时重读）要按多成员改：
- 攒的通知改为按订阅记（今天按"成员 × 订阅"记）：任何一个成员取走待发区，就把这个订阅攒着的通知全部
  定向重读、清空。
- "全都卡着"要求成员表非空：初始化中的整表订阅要攒 pending，不能因为空成员表（`all([])` 为真）被当成卡住、
  通知被停掉。
- 有人加入时，新成员没卡着，这个订阅就不再"全都卡着"：把它攒着的通知全部定向重读。否则要等哪个老成员
  取走待发区，新成员拿到的快照才会动。
- 有人在等订阅的结果（初始化、重读判定频道）时也不算卡住：等着的回复占着位，卡着的正是它后面的推送。
- 部分成员卡着时订阅照常处理，卡着的成员的待发区按 sub_id / row_id 合并，上限是这个订阅的数据量。
- 攒着通知的订阅按成员连接索引（`_parked_by`）：连接取走待发区时只看自己的，不扫它的全部订阅（一个慢连接
  能攒到 ping 超时约 40 秒，这期间每个连接每次取走待发区都要扫，§10 第 14 条）。

### 3.8 成本（预期，实测补在 §9）

- 每条通知：每个共享订阅只读、比对一次，与成员数无关。
- 每个成员：暂存一个小 dict、交付、唤醒、编码发送。聊天 2000 连接估算每条消息 60~120ms / worker。
- 订阅时：后加入的连接不读库、不 SUBSCRIBE（频道早已订着）、不补读；整表订阅不再每次全量读。
- 内存：同一查询的状态每个 worker 一份，另多一份快照（行对象与推送共用）。聊天从 2000 × 1024 个行订阅
  对象降到 1024 个，全量 GC 的停顿也会跟着缩短。

## 4. 正确性

- **成员的状态等于快照**：快照 = 初始行 + 按顺序暂存的更新；每个成员的待发区 = 它加入之后暂存的更新
  （合并过）；客户端按 row_id 覆盖 / 删除，最终等于快照。tick 中途加入的，交付时去掉加入时已暂存、之后没再
  变的（快照里已是这个值），其余照给，结果一样。
- **衔接**：回复排在所有推送之前（占位）。就绪前加入的，拿就绪时的快照，之后的更新全收；就绪后加入的，
  拿加入时的快照（同步取），之后的更新全收。回"没有"前重读的，拿重读之后的快照：它从加入起一直是成员，
  这之前交给它的更新排在回复后面，都是快照里已有的或更早的值，随后同一行的更新会再覆盖一次，最终仍等于
  快照。
- **回"没有"与 dev 一样新**：dev 在订阅时读库；这里回"没有"用的快照，是请求之后才开始的 tick 重读判定频道
  得到的。
- **尾随重读、补读的论证不变**：一个共享订阅就是一个订阅，一个队列、一条时间线；初始化期间跳过的通知，
  由生效时的补读覆盖。
- **读出错**：第一步 §6 的重试、换副本、退避照旧适用于共享订阅，所有成员一起等重试。

## 5. 测试计划（先写 red）

真实后端（`tests/test_backend_sub_hub.py`）：
- N 个连接订同一查询：初始读 1 次；每条消息 worker 内 1 次 ZRANGE、1 次新行读、1 次新行补读，与 N 无关；
  各连接都收到推送。
- 后来者加入：不读库；回复等于已有成员手里的状态（把已有成员收到的推送合并后比）。
- 初始化期间加入：几个连接同时订，初始读只有 1 次，回复都是就绪时的快照，之后的更新都收到。
- get 的行不存在：都回 None，不留订阅；整表超过上限：都回 None。
- `force=False` 且结果为空：不加入。
- 重复订阅：共享订阅回快照，不读库。
- RLS：两个连接订同一查询不共享、各自拿到自己可见的行；admin 之间共享。
- 键：`right=None` 与 `"None"` 不共享；`1` 与 `1.0` 不共享；`desc=1` 与 `True` 共享。
- 初始读出错：换副本重试后成功；重试用尽则等着的成员都失败。

竞态（`tests/test_backend_sub_race.py`，假 pubsub）：
- tick 中途加入：不会重复收到快照里已含的更新，之后的更新都收到。
- 初始化期间就有写入：推送都排在回复之后（占位）。
- 最后一个成员离开：订阅撤掉、频道退订。初始化期间成员全走了：初始化取消、占位撤掉。
- 背压：全员卡着时攒通知；有人加入时把攒着的重读；任一成员取走待发区时重读；初始化中的整表订阅不会被
  当成卡住。

服务端（`tests/test_websocket.py`）：订阅的初始读卡住时，同一连接的下一条消息（rpc）照常处理，回复仍按
顺序到达。

现有用例：`subscribe_get` 读期间推送抢先的两个用例（`UNKNOWN`），改为"初始化期间不推送，生效后补读推
最新的"。

PR 审查修正补的用例见 §10。

## 7. 备选方案与否决理由

- **get / range 保持同步回复**：整表订阅已经走占位，这样就要维护两套加入流程（用户选了统一走占位）。
- **快照由各类订阅自己维护（存完整行）**：私有订阅也得付这份内存；放在 hub 按暂存的更新维护，与比对逻辑
  无关。
- **共享 RLS 订阅，按成员过滤**：第一步已定不做。
- **初始读出错立即失败 / 一直重试**：用户定为有限重试后失败。前者一次抖动就让一批连接一起重连；后者 Redis
  长时间不可用时，订阅回复一直不来，排在它后面的 RPC 回复也跟着卡住。
- **退订后保留一段时间**：不做。
- **共用推送编码**：每帧 2.2µs，不值得。

### 9.1 Windows，进程内（2026-09-29）

环境同第一步设计稿 §12.1：Windows 11 + Docker Redis（主 + 1 副本，读走副本），单进程 = 1 个 worker，不含 ws 推送

**聊天扇出**（`benchmark/sub_fanout_chat.py`：每人订"最近 N 条"，每秒 2 条消息共 10 条）：

| 每条消息 | N=1024 200 连接 dev | 本分支 | N=50 200 连接 dev | 本分支 | N=1024 1000 连接 dev | 本分支 | 2000 连接 本分支 |
|---|---|---|---|---|---|---|---|
| worker CPU（每连接） | 688–727µs | 31–39µs | 219µs | 16µs | 559µs | 8µs | 7µs |
| 副本 CPU | 26.5–27.0ms | 1.8ms | 14.0ms | 1.6ms | 97.5ms | 1.8ms | 1.9ms |
| 副本出网 | 6.7MB | 35KB | 390KB | 2.9KB | 26.8MB | 35KB | 35KB |
| 副本读命令 | 200 ZRANGE + 201 HGETALL | 1 + 2 | 200 + 201 | 1 + 2 | 800 + 1001 | 1 + 2 | 1 + 2 |
| 订阅 + 补读消化完的 CPU（每连接） | 38.4–38.7ms | 0.3–0.5ms | 1.6ms | 0.2ms | 39.2ms | 0.1ms | 0.1ms |
| 常驻内存（每连接） | 508KB | 18KB | 35KB | 4KB | 461KB | 5KB | 3KB |

- 每条消息 worker 内只有 1 次 ZRANGE、1 次新行读、1 次新行频道订上后的补读，副本的开销与连接数无关。
- worker CPU 按"每条消息的总 CPU = 固定部分 + 每连接成本 × 连接数"拿 200、2000 连接两档拟合：每连接约 4µs
  （暂存、交付、唤醒 get_updates），固定部分约 6ms（含同进程写入的提交）。真实连接还要加每帧编码（Linux 实测
  2.2µs）和发送。
- dev 1000 连接时 ZRANGE 只有 800 次/条：各连接的比对跟不上消息，两条消息合进了同一次重读。

**AOI**（`benchmark/sub_budget.py`：200 连接、每连接订自己 zone 的 50 行、每秒 300 次写；组件是 `EVERYBODY`，同一
zone 的连接共享一个订阅）：

| 每次交付 | K=10（20 个 zone）dev | 本分支 | K=1（200 个 zone，没有可共享的）dev | 本分支 |
|---|---|---|---|---|
| worker CPU | 26.7µs | 26.1µs | 164–184µs | 125–213µs |
| 副本 CPU | 7.9µs | 9.0µs | 76–82µs | 70–89µs |
| 副本命令 | 0.26 | 0.26 | 2.51 | 2.52 |
| 写→交付延迟 p99 | 115.5ms | 116.1ms | 115–116ms | 109–116ms |
| 常驻内存（每连接） | 42KB | 21KB | 80KB | 98–101KB |
| 订阅耗时（每连接） | 8.4ms | 2.1ms | 10.3–10.5ms | 10.8–11.0ms |

- K=10：第一步已经让同一行在 worker 内一个 tick 只读一次，共享之后每次交付的 CPU 持平；省下的是订阅对象
  （内存减半）和订阅耗时（后加入的连接不读库、不补读）。
- K=1：每个订阅只有一个成员，走的路径与 dev 相同，CPU 在噪声内（这档负载只占 4~6% 核，三次运行波动约
  ±30%）。内存每连接多约 20KB，是可共享订阅的快照（50 行）：没人加入的可共享订阅也要付这份快照；RLS 订阅
  不维护快照。
