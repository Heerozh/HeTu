## 1. 背景

第一步把订阅处理搬到了 worker 级，但键带连接：同一查询在 worker 里仍有 N 个订阅对象，每条通知各自
ZRANGE、解码、求集合差。

Linux 实测（2000 个真实 ws 连接，每人订最近 1024 条聊天；第一步设计稿 §12.2、
`benchmark/sub_scenarios_result.md`）：
- 一个 worker 约 1 条/秒就打满，每条消息每个连接 450~550µs；
- tick 屏障让轻负载时所有连接等整批算完，推送 p50 从 629ms 升到 904ms；
- 堆 3~5GB（2000 × 1024 个行订阅对象），全量 GC 一次 0.5~1.7 秒。

共享之后，每条消息每个连接只剩暂存、交付、编码（实测每帧 2.2µs）、发送，估算 30~60µs，单 worker 约
10 条/秒量级；堆里也不再有成百万个行订阅对象。

## 2. 目标与非目标

目标：
- 非 RLS 组件的订阅，以及 admin 的订阅，按查询在 worker 内只有一个订阅对象，订了同一查询的连接都是它的
  成员。每条通知的读与比对在 worker 内只做一次。
- 后加入的连接用共享订阅的快照做回复，不读库、不补读。
- 回复排在之后的推送前面，快照与之后的推送衔接得上（§3.3、§4）。
- 共享订阅的初始读出错时有限重试（用户已定），顺带解决"首次读落到死副本，新订阅就失败"（第一步设计稿
  §4.9 末尾）。

非目标：
- RLS 订阅共享：按连接私有（第一步已定）；
- 跨 worker 共享；
- 多个连接共用推送编码：实测每帧 2.2µs，不值得；
- 最后一个成员离开后的保留期。

## 3. 设计

### 3.1 共享键

`(类别, 表, 查询, 可见性)`：
- **类别**：get / range / table。
- **表**：`(comp_cls, instance_name, cluster_id)`。不直接用 `TableReference`：`Table` 多一个 backend 字段，
  与同地址的 `TableReference` 互不相等。hub 本来就按 backend 分，不用再区分。
- **查询**：
  - get：row_id；
  - range：`(index_name, repr(left), repr(right), int(limit), bool(desc))`；
  - table：空。

  不用 sub_id 字符串做键：`right=None` 与字符串 `"None"` 拼出同一个 sub_id，共享后会让别人拿到另一个查询
  的结果。`repr` 在 None / bool / int / float / str 之间不会撞；`1` 与 `1.0` 分成两个键，只是少共享一些。
  `desc` 按 bool 规范化（客户端传 1 或 True 是一样的）。sub_id 仍按 `make_query_id_` 给客户端，记在各成员
  上（SDK 的 `MakeSubId` 在预测它，格式不能动）。
- **可见性**：订阅的 `rls_ctx` 为 None（组件不是 RLS，或 ctx 是 admin）时可以共享；否则私有。

hub 新增共享登记表 `_shared: dict[键, 订阅]`，私有订阅不进表。订阅关闭时（最后一个成员离开、初始化失败、
结果为空）同步从表里撤掉，前提是表里登记的还是它。

### 3.2 快照：成员手里的状态

可共享的订阅维护一份快照 `snapshot: dict[row_id, 行]`，也就是"成员的客户端手里现在有什么"：
- 初始化完成时，由初始读的可见行填上；
- 之后 hub 在 `_stage` 暂存更新时顺手改它（行为 None 就删）。在暂存时改、而不是交付时改：tick 中途加入的
  新成员拿到的快照已经含这次更新，而它不在这次暂存时的成员表里，不会再收到一次。
- 快照放在 hub 层、按暂存的更新维护，不碰三种订阅的比对逻辑。私有订阅不维护：没人会加入，每人一份背包
  的行对象也不是小数。
- 范围订阅的回复要按索引顺序：`IndexSubscription` 记下最近一次 ZRANGE 的 id 顺序（初始读、`_rerange`
  都拿得到），快照按它输出。只改非索引字段的更新不影响顺序。
- 整表订阅的快照就是整张表的可见行，最多 `MAX_TABLE_SUBSCRIPTION_ROWS` 行，每个 worker 一份。今天是每个
  连接一份 `known_ids`，每次订阅还要全量读一遍；共享后，后来的连接当场拿快照。
- 行对象不拷贝：暂存、快照、各成员的待发区和回复引用的是同一个 dict，之后都不再改它（每次更新都是新读
  出来的新 dict）。

### 3.3 订阅流程：统一走占位（用户已定）

get / range / table 三种订阅都拆成两段（今天只有整表订阅这样做）：

- **前半段**（在接收协程里）：权限检查、算 sub_id、同连接的重复订阅、找或建共享订阅、登记成员、计入订阅
  数。只有按非 id 索引的 `subscribe_get` 要先查一次索引拿到 row_id（它决定共享哪个订阅），这一次短读仍在
  前半段，同今天；其余的读、SUBSCRIBE、等共享订阅就绪都在后半段。
- **后半段**（后台任务，结果填进 push_queue 里的占位，同今天的整表订阅）：等订阅就绪，返回快照。

接收协程登记完就去处理下一条消息，不再等订阅的初始读。登录时连发的几个订阅也因此并发进行。

成员在前半段就登记进订阅的成员表，这是安全的：
- **回复在推送前面**：占位在登记之后、下一轮事件循环之前就进了 push_queue（`defer_sub_reply_` 的 eager 任务
  跑到后半段的第一个 await 就让出，随后同步放占位），发送循环按队列顺序发。之后交给这个成员的推送都排在
  回复后面。
- **就绪前登记的成员**：初始化期间订阅不产生任何更新（行 / 范围订阅还没生效，整表订阅只攒 pending）。
  它们的回复是**就绪那一刻**的快照：初始化结束时把快照一次交给当时等着的各成员（每个成员一个 future），
  之后的更新它们都收得到，两边衔接得上。
- **就绪后登记的成员**：前半段当场同步取快照，之后的更新都收得到。

订阅数在前半段登记时就计入 `count()`，`sub_call` 里的订阅数上限检查照旧。

已知的边角：push_queue 满（1024 条没发出去）时，放占位要等，这期间推送协程有机会插到占位前面。今天的
整表订阅也是这样，不在本稿处理。

### 3.4 共享订阅的初始化

第一个成员建订阅（订阅对象这时就建好，状态为空），初始化在 hub 自己的任务里跑，不挂在任何连接上：
- **行订阅**：attach（占位、订阅频道）→ 读行 → 记指纹、快照 → 生效。
- **范围订阅**：读 range 拿到初始行 → 填状态（`last_range_result`、各行指纹、id 顺序）→ attach → 生效。
- **整表订阅**：attach（立即生效，攒 pending）→ 隔 T 全量读 → `finish_init_`，同今天。

行 / 范围订阅在初始化期间**不生效**（tick 跳过它们）；生效时对全部频道定向补读一次（今天 `subscribe_get`
/ `subscribe_range` 本来也补读全部频道）。生效前被跳过的通知，补读时刻都晚于它们。这样一来，读的期间就
不会有推送抢到回复前面，`subscribe_get` 的 `UNKNOWN` 处理不再需要，删掉。私有订阅也走同一套初始化，
只有一条代码路径。

初始化的结果：
- 交给等着的成员做回复：共享订阅给就绪时的快照；私有订阅不维护快照，给初始读到的、按它的 ctx 可见的行
  （同今天）。
- get 的行不存在、整表超过行数上限：订阅不建，等着的成员都回 None，并撤掉成员身份。
- 范围订阅没有行时照样建；`force` 由各成员自己判断（§3.6）。

出错（用户已定：有限重试后失败）：
- 初始读出错时换一个随机副本，按 1、2、4 个 interval 退避重试，共 `INIT_RETRIES` 次（默认 3，约 0.7 秒）；
  还不行，才让等着的成员失败：后半段抛出 → 发送循环记日志、断开连接，同今天。
- attach（SUBSCRIBE）出错同样重试。
- 初始化期间成员全走了（连接断开、客户端 unsub）：取消初始化任务，撤掉占位。

### 3.5 离开

成员退订或连接关闭时，撤掉它的成员身份。成员撤空就关闭订阅、从共享登记表撤掉、退订没人要的频道，同第
一步。不设保留期。

### 3.6 回复的细节

- **range 的 `force=False`**：快照为空时这个成员不加入（撤掉成员身份），回 (None, [])，同今天。
- **同一连接的重复订阅**（sub_id 已登记）：共享订阅回快照，不读库；私有订阅没有快照，照旧重读。get 的行
  现在不可见 / 已删除、整表超过上限时撤掉旧订阅，同今天。
- 重复订阅的回复变成"订阅已推给客户端的内容"（今天是重新读的、可能落后的一份），docstring 与 SDK 注释
  跟着改。

### 3.7 背压与共享

第一步的背压（成员的推送全都卡着时订阅先不读、攒着通知，成员取走待发区时重读）要按多成员改：
- 攒的通知改为按订阅记（今天按"成员 × 订阅"记）：任何一个成员取走待发区，就把这个订阅攒着的通知全部
  定向重读、清空。
- "全都卡着"要求成员表非空：初始化中的整表订阅要攒 pending，不能因为空成员表（`all([])` 为真）被当成卡住、
  通知被停掉。
- 有人加入时，新成员没卡着，这个订阅就不再"全都卡着"：把它攒着的通知全部定向重读。否则要等哪个老成员
  取走待发区，新成员拿到的快照才会动。
- 部分成员卡着时订阅照常处理，卡着的成员的待发区按 sub_id / row_id 合并，上限是这个订阅的数据量。

### 3.8 成本（预期，实测补在 §9）

- 每条通知：每个共享订阅只读、比对一次，与成员数无关。
- 每个成员：暂存一个小 dict、交付、唤醒、编码发送。聊天 2000 连接估算每条消息 60~120ms / worker。
- 订阅时：后加入的连接不读库、不 SUBSCRIBE（频道早已订着）、不补读；整表订阅不再每次全量读。
- 内存：同一查询的状态每个 worker 一份，另多一份快照（行对象与推送共用）。聊天从 2000 × 1024 个行订阅
  对象降到 1024 个，全量 GC 的停顿也会跟着缩短。

## 4. 正确性

- **成员的状态等于快照**：快照 = 初始行 + 按顺序暂存的更新；每个成员的待发区 = 它加入之后暂存的更新
  （合并过）；客户端按 row_id 覆盖 / 删除，最终等于快照。
- **衔接**：回复排在所有推送之前（占位）。就绪前加入的，拿就绪时的快照，之后的更新全收；就绪后加入的，
  拿加入时的快照（同步取），之后的更新全收。
- **尾随重读、补读的论证不变**：一个共享订阅就是一个订阅，一个队列、一条时间线；初始化期间跳过的通知，
  由生效时的补读覆盖。
- **读出错**：第一步 §6 的重试、换副本、退避照旧适用于共享订阅，所有成员一起等重试。

## 5. 测试计划（先写 red）

真实后端（`tests/test_backend_sub_hub.py`）：
- N 个连接订同一查询：初始读 1 次；每条消息 worker 内 1 次 ZRANGE、1 次新行读、1 次新行补读，与 N 无关；
  各连接都收到推送。
- 后来者加入：不读库；回复等于已有成员手里的状态（把已有成员收到的推送合并后比）。
- 初始化期间加入：几个连接同时订，初始读只有 1 次，回复都是就绪时的快照，之后的更新都收到。
- get 的行不存在：都回 None，不留订阅；整表超过上限：都回 None。
- `force=False` 且结果为空：不加入。
- 重复订阅：共享订阅回快照，不读库。
- RLS：两个连接订同一查询不共享、各自拿到自己可见的行；admin 之间共享。
- 键：`right=None` 与 `"None"` 不共享；`1` 与 `1.0` 不共享；`desc=1` 与 `True` 共享。
- 初始读出错：换副本重试后成功；重试用尽则等着的成员都失败。

竞态（`tests/test_backend_sub_race.py`，假 pubsub）：
- tick 中途加入：不会重复收到快照里已含的更新，之后的更新都收到。
- 初始化期间就有写入：推送都排在回复之后（占位）。
- 最后一个成员离开：订阅撤掉、频道退订。初始化期间成员全走了：初始化取消、占位撤掉。
- 背压：全员卡着时攒通知；有人加入时把攒着的重读；任一成员取走待发区时重读；初始化中的整表订阅不会被
  当成卡住。

服务端（`tests/test_websocket.py`）：订阅的初始读卡住时，同一连接的下一条消息（rpc）照常处理，回复仍按
顺序到达。

现有用例：`subscribe_get` 读期间推送抢先的两个用例（`UNKNOWN`），改为"初始化期间不推送，生效后补读推
最新的"。

## 7. 备选方案与否决理由

- **get / range 保持同步回复**：整表订阅已经走占位，这样就要维护两套加入流程（用户选了统一走占位）。
- **快照由各类订阅自己维护（存完整行）**：私有订阅也得付这份内存；放在 hub 按暂存的更新维护，与比对逻辑
  无关。
- **共享 RLS 订阅，按成员过滤**：第一步已定不做。
- **初始读出错立即失败 / 一直重试**：用户定为有限重试后失败。前者一次抖动就让一批连接一起重连；后者 Redis
  长时间不可用时，订阅回复一直不来，排在它后面的 RPC 回复也跟着卡住。
- **退订后保留一段时间**：不做。
- **共用推送编码**：每帧 2.2µs，不值得。

## 8. 已定事项（2026-09-29）

1. 所有订阅的回复都走占位（get / range 也在后台完成），成员在前半段登记。
2. 共享订阅的初始读出错：换副本、退避，有限重试后才失败。
3. 延续第一步：RLS 订阅私有；tick 里读失败重读、不断开。

## 9. 实测（实施后补）
