- 影响范围（§2、§3）：`hetu/server/websocket.py`（发送循环）、`hetu/server/receiver.py`（删

## 1. 背景

第二步之后，聊天（2000 连接各订最近 1024 条）单 worker 能到约 200 条/秒，剩下的成本几乎都在每个连接的推送上：
每个连接每个 interval 最多一帧，每帧约 19.8µs worker CPU。聊天 10 条/秒（每秒 2 万帧）的 cProfile：

- 编码约 20%（zlib 11%、加密 4.5%、jsonb 2%）；
- `ws.send` 约 20%（Sanic + websockets 分帧 + send）；
- 交付之后到发送循环拿到消息的两次任务交接约 40%；
- hub 的 tick（含交付给 2000 个成员）9%。

同时 GC 在两个场景都造成几十到两百多毫秒的停顿（§4）。本稿给出两处的实测与方案。实验都在压测脚本的临时
副本里做（§5），仓库里的压测脚本没有这些开关。

## 2. 推送路径：发送循环直接取待发区

### 2.1 现状

每个连接三个协程：接收协程（`client_handler`）、订阅推送协程（`subscription_handler`）、发送循环
（`websocket_connection` 本体）。一帧推送：

1. hub 的 `_deliver` 放进门面的待发区，`Event.set`；
2. `subscription_handler` 醒来：`get_updates` 里 `asyncio.timeout_at(None)` + `Event.wait` 返回，按 sub_id
   逐条 `await push_queue.put(["updt", sub_id, 行])`；
3. 发送循环醒来：`push_queue.get` 取出，编码，`ws.send`。

`push_queue`（上限 1024）同时装 RPC 回复、订阅回复的占位（future）、推送和 `PUSH_CLOSE`，发送循环按 FIFO 发。

### 2.2 设计

去掉 `subscription_handler`，发送循环自己取待发区：

- **叫醒**：门面记下发送循环的叫醒函数（`bind_sender_`）。待发区交来更新、而发送循环正空闲等待时，
  `deliver_` 调它往 `push_queue` 放一个哨兵（`PUSH_UPDATES`）；每段空闲最多叫一次（醒来时清标记）。
- **顺序**：发送循环只在 `push_queue` 为空时取待发区（`take_updates_`），逐个 sub_id 发 `updt`。订阅回复的
  占位是先放进队列、再登记成员的（第二步 §3.3），队列空了就说明登记之前放的占位都已发出，这个订阅的推送
  不会抢到它的回复前面。
- **推送卡住**（`stalled_`，hub 据此停读、攒通知）：待发区有东西，而发送循环不在空闲等待。发送循环在等
  `push_queue.get()` 和等订阅回复的占位时算空闲（`idle_(True)`），同今天：今天等占位期间
  `subscription_handler` 照常取待发区，推送排进队列。Sanic 的 `ws.send` 不拥塞时一路不让出（`conn_mutex`
  没人争、`_can_write` 已置位），所以正常发送时 hub 看不到"不空闲、待发区又有东西"；只有 `ws.send` 卡在
  drain 上（客户端网络拥塞）才算卡住。
- **慢客户端**：推送留在待发区里按 sub_id / row_id 合并，不再在 `push_queue` 里堆最多 1024 帧未合并的更新；
  等占位期间多次更新同一行，回复之后只推一帧最新的。
- `get_updates` 保留（测试、手动模式），改为基于 `take_updates_`；同一个门面只用一种取法。
- 删掉 `subscription_handler`（它按 `RedisConnectionError` 断开的分支在 hub 模式下已经走不到：`get_updates`
  不碰 I/O）与拆连接时取消它的步骤（`subs_task_id`）。每个连接少一个 Task。

发送循环的骨架：

```python
while True:
    if push_queue.empty():
        updates = broker.take_updates_()
        if updates:
            ...逐个 sub_id 编码、ws.send、发送计数
            continue
        broker.idle_(True)
        try:
            reply = await push_queue.get()
        finally:
            broker.idle_(False)
    else:
        reply = push_queue.get_nowait()
    if reply is PUSH_UPDATES:
        continue
    ...PUSH_CLOSE、占位（等的期间 idle_(True)）、编码发送，同今天
```

### 2.3 正确性

- **不会漏叫醒**：发送循环在"待发区为空"与 `idle_(True)`、`await push_queue.get()` 之间没有 await，hub 交来
  更新只可能发生在它挂起之后；这时 `_waiting` 为真、标记未置，`deliver_` 一定叫醒它。叫醒时队列满
  （`QueueFull`）就不放：队列非空，发送循环不会挂在 `get()` 上，发完队列会回来取待发区。
- **回复在推送前面**：见 §2.2 顺序。RPC 回复会先于同时在等的推送发出（今天两者在队列里按 FIFO 交错）；
  客户端本来就不能依赖两者的先后。客户端一直发 RPC 时推送会被推后，有发送频率上限兜底。
- **背压**：卡住时 hub 停读、攒通知（第一步），发送循环取走待发区时 `resume_` 重读，同 `get_updates`。

### 2.4 原型实测

原型约 80 行，`test_websocket.py` 33 个用例全过。同一份压测脚本，HEAD（`546f3a7`）对原型：

| 场景 | worker 核 | 每条（次）周期 | 推送 p99 | RPC 往返 p99 / 最大 | GC 每秒耗时 |
|---|---|---|---|---|---|
| 聊天 10 条/秒 | 0.396 → 0.321 | 166M → 132M（-21%） | 151 → 133ms | 41 / 140 → 21 / 40ms | 51 → 0.2ms |
| 聊天 100 条/秒 | 0.603 → 0.525 | 26.0M → 22.3M（-14%） | 179 → 158ms | 59 / 156 → 55 / 59ms | 53 → 0.9ms |
| 聊天 200 条/秒 | 0.739 → 0.668 | 16.1M → 14.4M（-11%） | 206 → 178ms | 74 / 162 → 79 / 81ms | 55 → 0.8ms |
| 背包增删 2000 次/秒 | 0.409 → 0.403 | 730k → 715k（-2%） | 相同 | 相同 | 相同 |
| 背包增删 4000 次/秒 | 0.625 → 0.610 | 618k → 600k（-3%） | 134 → 125ms | 相近 | 相近 |

- 每帧 19.8 → 16.0µs。背包回到第一步的 594~609k，第二步多出的 2~3% 被抵掉。
- 聊天省下的约三分之二来自 GC。HEAD 在聊天下每秒约 9 次年轻代回收，每 30 秒还有 2~3 次约 105ms 的全量回收，
  GC 占 worker CPU 的 13%。1 秒垃圾采样是 0 个，不是产生了垃圾：每轮扇出时 2000 个连接的在途对象（排在队列里
  的帧、`subscription_handler` 的协程与 future）同时存活，净分配超过阈值 2000 就触发回收，把它们提前晋升进
  老年代，进而拖出全量回收。原型不在队列里排帧，同时存活的对象少，30 秒只回收 1~5 次。

### 2.5 测试计划（先 red）

竞态（`tests/test_backend_sub_race.py`，假 pubsub）：
- 发送循环空闲时交来更新叫醒一次，同一段空闲里再交来不重复叫；醒来再空闲后又能叫醒。
- 空闲时交来的更新不算卡住，hub 照常处理、合并进待发区；不空闲且待发区有东西算卡住，通知攒着；
  `take_updates_` 取走后重读攒着的。
- `take_updates_` 不等待：待发区空就返回空 dict。

服务端（`tests/test_websocket.py`）：同一连接上订阅回复还在等初始化时，已有订阅的同一行被改了几次，回复之后
只收到一帧推送（最新值），且排在回复后面。今天是回复后逐帧收到每次的值。

## 3. 遗留 bug：退订清空待发区后，攒着的通知没人重读

第一步引入背压时就有。连接推送卡着（待发区有东西、没人取）时，另一个订阅 Z 的通知被攒下（`_park`，成员
全都卡着）。这时客户端退订了待发区里唯一有东西的订阅，待发区清空：连接不算卡住了，但 Z 攒着的通知只在取走
待发区时（`resume_`）或有新成员加入时重读，而待发区已经空了，不会再有"取走"。Z 的那次变动一直推不到客户端，
直到它的频道再来通知。比如背包里新进来的物品一直不出现。

修法：`unsubscribe` 撤掉待发区里的那份之后，待发区空了就 `resume_` 一次，同取走待发区。草稿用例（两个订阅，
一个卡着待发区、一个的通知被攒下，退订前一个）在 `546f3a7` 上拿到 `{}`，加一行后通过。

## 4. GC（建议，未实施）

### 4.1 事实

- Python 3.14.7 的 GC 仍是分代、非增量（3.14 的 `gc.c`），默认阈值 (2000, 10, 10)。全量回收要中代回收满 10 次，
  且上次全量回收以来晋升进老年代的对象不少于老年代总数的 25%。
- 3.14 不再把只含原子值的 dict 移出追踪：每一行数据都是 GC 对象。
- 触发计数是"分配数减释放数"，老对象死亡也会抵扣，年轻代阈值管不住年轻代的大小。实测慢的年轻代回收发生时
  年轻代有 4.4 万~11.4 万个对象，一次 11~34ms；中代 6.3 万~11.6 万个，一次 20~44ms。
- 成本：全量回收约 160~175ns/对象，年轻代约 300ns/对象（这台笔记本）。

### 4.2 堆里是什么

- 每个连接约 285 个对象，基本是 asyncio 与 Sanic 的：6 个 Task、16 个协程、12 个 contextvars.Context、
  9 个 Event、19 个 deque、22 个函数、18 个 cell 等。
- 私有行订阅每行约 4 个：`RowSubscription`、约 2 个 set、1 个 dict。
- 聊天 57 万个对象，全量回收 91ms；背包（每人 30 件）82.5 万个，全量回收 144ms。
- 断开连接每个留下约 60 个成环的对象，只能靠全量回收收掉：Sanic / websockets 的连接对象（`WebSocketProtocol`、
  `Http`、`WebsocketImplProtocol`、`ServerProtocol`、`StreamReader`，以及它们的 Event、Lock、deque、Queue）
  被一个 `EOFError` 的 traceback 串成环；还有 HeTu 的 `SystemContext` 与 `SystemCaller` 互相引用
  （`context.systems = system_caller`）。

### 4.3 停顿从哪来

- 全量回收：聊天（HEAD）每 30 秒 2~3 次、每次约 105ms；背包 4000 次/秒时约每 1.5 分钟一次、210~240ms。
- 背包的年轻代 / 中代：年轻代约每秒一次、11~37ms，中代约每 10 秒一次、20~77ms（原因见 §4.1 第三条）。
- 聊天（HEAD）的年轻代：每秒约 9 次，每次 5~10ms，GC 合计占 worker CPU 的 13%（原因见 §2.4）。

### 4.4 各方案实测（HEAD 推送路径，每种配置 2~3 个 30 秒窗口）

背包增删 4000 次/秒：

| 配置 | 30 秒内回收（年轻/中/全量） | 最长停顿 | RPC 往返最大 | 推送 p99 | 每次操作周期 |
|---|---|---|---|---|---|
| 默认 | 26~33 / 2~3 / 约每 90 秒 1 次 | 年轻 27~37ms、中代 53~64ms、全量 210~240ms | 49~68ms | 134ms | 618k |
| 2000 连接建好后冻结 | 26~37 / 2~3 / 0 | 年轻 30~46ms、中代 51~77ms | 46~73ms | 131~144ms | 614~620k |
| 阈值 20000 | 0 / 0 / 0 | — | 2.4~3.1ms | 110ms | 608~614k |
| 阈值 100000 | 0 / 0 / 0 | — | 2.6~5.1ms | 110ms | 606~611k |
| 每 100ms 手动回收年轻代 | 295 / 0 / 0 | 3ms | 2.5~3.7ms | 110ms | 628~636k |

聊天 50 条/秒：

| 配置 | 30 秒内回收（年轻/中/全量） | 全量回收一次 | RPC 往返最大 | worker 核 |
|---|---|---|---|---|
| 默认 | 271 / 24 / 2~3 | 106~108ms | 143ms | 0.50~0.51 |
| 冻结 | 273 / 24 / 2 | 12ms | 61~63ms | 0.50 |
| 阈值 20000 | 0 / 0 / 0 | — | 60~61ms | 0.46~0.47（-8%） |
| 每 100ms 手动回收年轻代 | 528 / 46 / 4 | 103ms | 136~145ms | 0.52 |

- 聊天 RPC 往返最大值约 60ms 就降不下去了，那是一轮扇出本身的时长，不是 GC。
- 冻结：只让全量回收变便宜（聊天 106 → 12ms），年轻代、中代不变。冻结之后断开的连接，那约 60 个成环对象留在
  冻结区（泄漏测试：断开全部 2000 个后冻结区还有 23 万个，解冻后全量回收收掉 12.6 万个）。
- 手动回收年轻代：定时回收总把计数清零，自动回收不再触发，中代一次都没回收，晋升上去的对象（含成环垃圾）
  一直积在中代；聊天下回收反而更多。

### 4.5 建议（按优先级）

1. 先做 §2 的推送路径改造：聊天的 GC 基本消失，不用调参。
2. worker 启动时把年轻代阈值调到约 2 万，做成配置项（如 `GC_THRESHOLD: [20000, 10, 10]`），另两个不动。
   - 收益：背包类增删场景里几十毫秒的年轻代、中代停顿在稳态下消失，推送 p99 134 → 110ms，RPC 往返最大
     50~70 → 3ms；晋升少了，全量回收也跟着少；CPU 略省。
   - 代价（推断，没有直接测到）：回收变得很少，但一旦发生，年轻代里是上次回收以来还活着的全部对象，背包最坏
     约 25 万个、约 75ms，间隔以分钟计；成环垃圾最多多留 2 万个对象，几 MB。
   - 2 万与 10 万在背包里效果一样，取小的更保守。
3. 启动完成、开始接连接之前 `gc.collect(); gc.freeze()` 一次：启动后常驻的约 13 万个对象（模块、组件定义等）
   不再参与每次全量回收，估计每次少约 20ms。它们本来就不会释放，没有泄漏风险。
4. 不建议：运行中周期性冻结（冻结过的连接断开后泄漏，必须定期解冻 + 全量回收，停顿换个时间集中出现）；
   定时手动回收年轻代（见 §4.4）；`gc.disable()`。
5. 顺手：拆连接时断开 `SystemContext` 与 `SystemCaller` 的互相引用；用 `gc.callbacks` 记录超过阈值（如 20ms）
   的停顿进日志或指标。停顿与每个 worker 的对象数成正比，单机连接多时多开 worker 能直接摊薄。

## 5. 实验方法

压测脚本（`benchmark/sub_scenarios_ws.py`、`sub_scenarios_app.py`）复制到临时目录后加了这些开关，没进仓库，
要做 GC 时可以并进压测脚本：

- `HETU_BENCH_GC_THRESHOLD="t0,t1,t2"`：服务器启动时 `gc.set_threshold`；
- `HETU_BENCH_GC_FREEZE=1`：连接建好后 `gc.collect(); gc.freeze()`；
- `HETU_BENCH_GC_YOUNG_MS=100`：后台线程定时 `gc.collect(0)`；
- `HETU_BENCH_GC_PROBE=1`：连接建好后按类型数一遍被追踪的对象、量一次全量回收；
- `HETU_BENCH_GC_GARBAGE=1`：窗口开始时用 `DEBUG_SAVEALL` 采 1 秒只能靠循环回收的垃圾；
- `HETU_BENCH_GC_LEAKTEST=1`：跑完断开全部客户端，看冻结区剩多少、解冻后全量回收收掉什么；
- `HETU_BENCH_GC_DEBUG=1`：`gc.DEBUG_STATS`，每次回收的各代对象数进服务器日志；
- `HETU_BENCH_GC_TRACE=1`：超过 5ms 的回收记下回收前年轻代、中代的对象数；
- 每步结果多了各代的回收次数与最长停顿（`gc_n_by_gen`、`gc_max_ms_by_gen`）。
