# 订阅驱动的 worker 行缓存（RowCache）实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把"本 worker 有客户端订阅的行"留在进程内存里：事务读命中 0 往返；commit 写穿后同一连接反复读写同一行只剩 commit 那 1 次往返；订阅推送从同一份缓存取行（自己写的行推送 0 次读，别人写的行每 worker 只读 1 次）。顺带修掉既有的"订阅推送读随机副本、旧值一直旧到下次写"问题。

**Architecture:** 行通知改为 commit 主动 PUBLISH 并携带新 `_version`（Lua 不改，Python 组 `publishes`）；进程级 `RowCache` 只对本 worker 有订阅（hub 已 ack）的行激活，按行记版本下限 floor；`CachedRowReader` 是事务与订阅共用的读路径——命中直接返回，miss 时副本读回版本低于 floor 即判滞后改走**权威读**（master 上执行、不带 shebang 的 Lua `HGETALL`，代理模式下唯一一定到主节点的读）；commit 成功写穿、RACE 按 Lua 回显版本抬 floor；易失组件不缓存、`direct_set` 明确不通知；`RowSubscription` 的 per-tick 缓存删除，`subscribe_get` 先订后读。设计稿：`docs/superpowers/specs/2026-09-22-row-cache-design.md`（第 3 版）。

**Tech Stack:** Python 3.14、Redis pubsub / Lua、numpy structured record、pytest（Redis 需 Docker，sqlite 免）。

## Context

#142 之后写事务已压到 `insert` 1 RTT、`get(id)+update` 2 RTT，剩下的那 1 次是事务里的读。本 worker
的订阅系统本来就在实时跟踪客户端订阅的每一行，却没人复用它。目标：把"本 worker 有客户端订阅的行"
留在进程内存里——事务读命中 0 往返、commit 写穿后同一连接反复读写同一行只剩 commit 1 次、订阅推送也从
同一份缓存取行（自己写的行推送 0 次读，别人写的行每 worker 只读 1 次）。

一致性不靠 TTL：**行通知改为 commit 主动 PUBLISH 并携带新 `_version`**（keyspace 事件不带内容），
缓存对每个激活行记版本下限 floor，副本读回版本低于 floor 即判滞后改走**权威读**（master 上执行的
Lua `HGETALL`——代理模式下普通 `HGETALL` 会被送到副本，只有脚本一定到主节点），写事务另有 VER 兜底。
顺带修掉既有的"订阅推送读随机副本、旧值一直旧到下次写"问题（代理拓扑下尤其明显）。

已拍板的决策（见 spec §1）：只缓存有订阅的行；行通知带版本；floor + 权威读（不做副本亲和）；权威读一律
EVALSHA（脚本**不带** `#!lua` shebang）；commit 写穿；易失组件不缓存、`direct_set` 明确不通知；维护工具
不补通知（只在停服时用）；`configure_servant` 目标 `Kghz` → `Kz`；订阅侧删 per-tick ContextVar 缓存、
共用 `CachedRowReader`、`subscribe_get` 先订后读；`batch.py` 删除。

     `>=` 收并抬 floor；`DELETED` 时非权威拒、权威收；失活再激活后旧 lease（epoch 过期）拒。
  3. `notify`：版本高于缓存行 → 逐出 + floor 抬；低于 → 不逐出、floor 不降（`max`）；`0` → 逐出 +
     `DELETED`；`DELETED` 后 `notify(1)` → floor 1；未激活频道 `notify` 无副作用。
  4. `put_committed`：激活行存入、floor = 版本；未激活丢弃；版本低于已知 floor 不覆盖。

  6. 两个 owner 激活同一频道，一个 `deactivate` 后另一个的 lease 仍可 fill；全部失活 → 行、floor 都清。
  7. `clear`；`stats`（hits / misses / authoritative_reads / size）。
  8. `CachedRowReader.get`：无缓存对象或易失组件 → 只调 `fallback.get`；未激活 → `fallback.get`；
     激活 + floor 未知 → 只调 `master.get_authoritative` 并填充；floor 已知 + fallback 返回低版本 →
     再调权威读、缓存存权威行；命中 → 零调用。`get_many`：混合命中 / 未激活 / 未知 / 滞后四类 id，

## 风险与注意

- **升级耦合**：行通知改 PUBLISH 后老写入方的更新新订阅方收不到——PR 描述与 `operations.md` 写明
  所有写入方一起升级（与 #142 值频道同类）。
- **权威读脚本不带 shebang**：路由到主节点靠命令名；带 shebang 而不声明 `no-writes` 会在主节点
  `min-replicas-to-write` 不满足时连只读脚本一起拒。
- **hub 回调在监听协程里同步跑**：`notify` / `activate` 只做 dict 操作，不 await。
- **多 hub（多 servant）**：`activate` 按 owner 计数、`notify` 用 `max` 幂等，跨 hub 乱序最坏多一次
  权威读。
- **内存**：订阅行常驻，`row_cache_max_rows` 默认 200k 封顶；LRU 只丢行不丢激活 / floor。
- **测试顺序敏感**（记忆 `test-order-sensitivity`）：起服类测试全量跑一次才算数。

## 效果与验证

- 单元：`test_row_cache_hit_after_subscribe`（订阅后第二次事务读 0 次远程）、
  `test_row_cache_write_through`（读-改-写后下一事务 0 次读）、`test_sub_push_uses_row_cache`
  （两连接订同一行只 1 次读、自己写的行推送 0 次读）。
- 端到端（RTT 探针）：订阅中的行 `get(id)` 只读 1→0、`get(id)+update` 稳态 2→1、`range` 10 行 2→1、
  订阅推送每 worker 每次变更 N→1 / 自写 →0；代理模式下推送不再出现"旧值一直旧到下次写"。
