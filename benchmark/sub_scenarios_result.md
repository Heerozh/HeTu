# 大量连接下的订阅压测（worker 级订阅器，Linux）

脚本：`sub_scenarios_ws.py`（场景压测）、`sub_servant_down.py`（副本挂掉）、`sub_servant_slow.py`（副本变慢）、
`push_encode_cost.py`（推送编码成本）。设计见
`docs/superpowers/specs/2026-09-28-worker-subscriptions-design.md`（§4.8 合批窗口、§4.9 分到各副本）。

## 环境与方法

- Intel Core Ultra X7 358H 笔记本（P 核 0-3、E 核 4-11、低功耗 E 核 12-15），CachyOS（Linux 7.2），性能模式；
  Python 3.14.7 + uvloop 0.22；Redis 8.10.2（docker，host 网络）。
- 真实 `hetu start`，`WORKER_NUM: 1`（Sanic 单进程），绑 CPU0；Redis 主 / 副本各绑 CPU2 / 3；8 个客户端进程
  在 E 核上开 2000 条真实 WebSocket（jsonb + zlib + crypto 握手、`elevate` 登录、订阅）；写进程在低功耗
  E 核，经 Session.commit 直写；RPC 探针（一个不订阅的连接每 20ms ping 一次）在 CPU1。
- 每档写入跑 5 秒预热 + 30 秒计时窗口。**开销按 worker 的 user 态周期数比**（`perf stat`）：笔记本 P 核
  频率随负载在 2.0~4.5GHz 之间变，CPU 时间跨负载、跨代码不可比。每档结束后等 worker 闲下来，核对"每个
  客户端手里的行 == master 上的行"：下面所有窗口都是 0 差异，2000 个连接全程没有断开。
- 版本：**dev**（`b0f1306`，每连接一个 MQ 队列）；**第一版**（worker 级订阅器，`e52fda8`，没有合批窗口、
  订阅通知随机绑一个副本）；**最终**（加上 5ms 合批窗口、订阅通知分到各副本）。dev 用 `--server-pythonpath`
  跑，复测两个点与几小时前一致（2000 次/秒增删 1084 vs 1089 kcycles/op）。
- 第二步（同一查询在 worker 内共享订阅）另起一节，紧接在下面；再往后是第一步的结果。

## 发送循环直接取待发区（2026-09-29）

设计与原因见 `docs/superpowers/specs/2026-09-29-push-path-and-gc-design.md` §2：去掉每连接的
`subscription_handler`，发送循环在 push_queue 为空时直接取门面的待发区。环境、方法同上；实现后（`a4c0a4a`）与
改之前（`546f3a7`）同一时段各跑一遍，聊天每档一个 30 秒窗口，背包 4000 次/秒三个。

| 场景 | worker 核 | 每条（次）周期 | 推送 p99 | RPC 往返 p99 / 最大 | 30 秒内 GC 回收（年轻/中/全量） |
|---|---|---|---|---|---|
| 聊天 10 条/秒 | 0.400 → 0.337 | 168M → 137M（-18%） | 148 → 136ms | 41 / 151 → 22 / 55ms | 275 / 25 / 3 → 0 / 0 / 0 |
| 聊天 100 条/秒 | 0.601 → 0.543 | 26.0M → 23.0M（-12%） | 180 → 161ms | 61 / 159 → 57 / 63ms | 272 / 24 / 2 → 7 / 1 / 0 |
| 聊天 200 条/秒 | 0.744 → 0.669 | 16.2M → 14.4M（-11%） | 205 → 178ms | 76 / 160 → 69 / 79ms | 272 / 25 / 2 → 3 / 1 / 0 |
| 背包增删 2000 次/秒 | 0.408 → 0.406 | 727k → 723k（-0.6%） | 相同 | 相同 | 相近 |
| 背包增删 4000 次/秒 | 0.626 → 0.619 | 619k → 611k（-1.4%） | 137~143 → 131~133ms | 相近 | 相近 |

- 聊天每帧 20.0 → 16.8µs（10 条/秒）；背包每次操作只推一帧，省得少。
- 聊天省下的约三分之二来自 GC：以前每轮扇出时 2000 个连接的在途对象（排在 push_queue 里的帧、
  `subscription_handler` 的协程与 future）同时存活，净分配超过阈值就触发年轻代回收，把它们提前晋升，进而拖出
  约 105ms 的全量回收（每 30 秒 2~3 次）。上一节聊天的 RPC 最大 136~160ms 就是它，改后降到 55~79ms（剩下的
  是一轮扇出本身）。
- 背包 4000 次/秒两边都各有一个窗口碰上约 230ms 的全量回收（推送 p99 217 / 245ms），上表是没碰上的窗口。
  背包的 GC 停顿与改法建议见设计稿 §4。
- 所有窗口核对一致性都是 0 差异，消息全部送达，服务器日志 0 条错误。

## 等推送的调用（rpcs，2026-10-10）

`--rpcs-rate` / `--rpcs-conns` / `--rpcs-cmd`：在场景负载之上让一部分连接调 `rpcs_write`，量 sync 与推送的先后、
δ（commit 返回 → 通知进 hub 队列）与栅栏的额外开销。结果与结论见
`docs/superpowers/specs/2026-10-10-rpcs-sync-design.md` §8.2：背包 / 聊天共 19200 次调用 sync 先于推送 0 次，δ p99
< 1ms，20ms 余量维持；每次调用比同样的 `rpc` 多约 24µs（+7%）。量开销时设 `HETU_BENCH_NO_FENCE_PROBE=1` 不装
worker 里的打点。

以下是第一步的结果。

- **第一版为什么反而更费**：`MQClient.get_message` 只弹出已满一个 interval 的通知，通知接连不断时，hub 弹一批
  跑一个 tick、跑完马上弹下一批：2000 次/秒增删时每秒约 1500 个 tick、平均每个 2.04 条；只改不增删 4000
  次/秒时每秒约 3000 个、每个 1.34 条。每 tick 的固定开销（建任务、gather、等订阅回执、预读往返……）被放大上千
  倍，合批几乎不生效。cProfile 看 Python 函数本身的耗时第一版还略少，多出的周期在 asyncio / uvloop 的调度里。
- **合批窗口**：相邻 tick 的开始至少隔 `TICK_SPACING_INTERVALS` 个 interval。窗口大小的对比（4000 次/秒增删，
  每种两个 30 秒窗口）：

  | 窗口 | worker 核 | kcycles/op | 每 tick 条数 | p50 / p99 | RPC p99 / 最大 | 全量 GC |
  |---|---|---|---|---|---|---|
  | 无 | 0.89 | 925 | 3.6 | 102 / 104~134ms | 1.0~1.6 / 38~72ms | 无 |
  | 5ms（默认） | 0.61 | 595 | 31 | 106 / 128~151ms | 2.4 / 56~75ms | 无 |
  | 10ms | 0.58 | 571 | 61 | 110 / 140~224ms | 4.9~6.9 / 25~215ms | 2 个窗口里 1 个（另两次同样的压测各 1 次） |
  | 25ms | 0.63 | 642 | 169 | 125 / 416ms | 20 / 241ms | 每秒 0.3 次 |

  窗口越大，一个 tick 里同时存活的对象越多，越容易触发全量 GC（2000 连接、约 730MB 时一次约 230ms），事件
  循环一口气处理得也越久。5ms 已拿到大部分收益，默认取它。
- **饱和时**：dev 每个连接各自处理，4000 次/秒时尾延迟和 RPC 响应明显变差；worker 级订阅器批量处理，扛得住。

- 双副本（通知分到两个副本，10ms 窗口时测）：2000 次/秒增删 711 kcycles/op，单副本 674，多开一条 pubsub
  连接约多 5%；延迟不变。
- 订阅阶段（连接 + 登录 + 订阅 30 行）：各版本都约 3.6ms worker CPU/连接，2000 连接 32 秒；RSS 约 730~750MB。

## 聊天：每人订 ChatMessage 最近 1024 条

2000 个连接各订 `id` 倒序最近 1024 条（同 examples/chat），写进程按速率发消息。

| 条/秒 | 版本 | worker 核 | 每条消息 Mcycles（每连接 µs） | 推送 p50 / p99 | 全员送达 p50 / p99 | RPC p99 / 最大 |
|---|---|---|---|---|---|---|
| 0.5 | dev | 0.55 | 4960（550） | 629 / 1763ms | 1.02 / 1.86s | 68 / 848ms |
| | 最终 | 0.45 | 4019（445） | 904 / 1450ms | 0.91 / 1.45s | 64 / 569ms |
| 1 | dev | 0.99（饱和） | 4494（492） | 800 / 2362ms | 2.61 / 3.54s | 89 / 976ms |
| | 最终 | 0.91 | 4162（445） | 959 / 1654ms | 1.01 / 1.66s | 92 / 634ms |
| 2 | dev | 0.99 | 2251 | 924 / 3170ms | 2.69 / 4.27s | 128 / 1182ms |
| | 最终 | 0.99 | 2259 | 1165 / 2387ms | 1.78 / 2.51s | 122 / 708ms |
| 5 | dev | 0.99 | 908 | 1862 / 6338ms | 5.40 / 9.07s | 136 / 1718ms |
| | 最终 | 0.99 | 908 | 1425 / 2983ms | 2.04 / 3.29s | 106 / 888ms |

- 第一版与最终在这个场景下一样（聊天的通知很稀，合批窗口不起作用）。
- **一个 worker 在约 1 条/秒时就打满**，两版都是：每条消息每个连接都要 ZRANGE 1024 个 id、解码、做集合差，
  约 450~550µs。饱和后按 tick 合并处理，吞吐不掉，但延迟随积压增长。副本每条消息出网约 70MB。
- worker 级订阅器的改善：每条消息周期少 7~19%，内存 5.0GB → 3.0GB，订阅阶段 39 → 25ms/连接；过载时全员
  送达的尾延迟好得多（5 条/秒：9.1s → 3.3s）。但轻负载时 tick 屏障让所有连接等整批算完（约 0.9 秒）才收到，
  p50 比 dev 高（629 → 904ms）。
- 全量 GC：堆有 3~5GB（2000 个订阅 × 1024 个行订阅对象），RPC 最大卡顿 0.5~1.7 秒，两版都有。
- 结论：这个规模必须等"同一查询在 worker 内共享一个订阅对象"（设计稿 §10）。共享之后每条消息每个连接只剩
  暂存、交付、编码、发送：编码实测每帧 2.2µs、59 字节（`push_encode_cost.py`），整条推送路径按背包只改不增删
  的数据估约 30~60µs，2000 连接每条消息约 60~120ms，单 worker 大约能到 10 条/秒量级（估算）。第二步实测见
  上一节：每帧约 19µs，且每个连接每个 interval 最多一帧，单 worker 约 200 条/秒才到头。

两个副本，`docker stop` 其中一个；进程内 20 个 broker，各订最近 10 条聊天。

|---|---|---|---|
| dev | 5/20（另有 9 个读出错，生产里会被断开） | 7/20 | 新订阅 20/20 |
| 第一版（杀掉 hub 绑定的副本） | **0/20** | **0/20** | 20/20，20/20 |
| 最终 | 20/20 | 11/20 | 20/20，20/20 |

最终版新订阅失败的 9 个都是订阅时的首次读随机落到了死掉的副本（读路径与 dev 相同，没改）。副本要带
`--notify-keyspace-events` 启动：HeTu 只在启动时 `CONFIG SET`，副本重启后配置丢失，keyspace 通知就没了，
看起来像订阅不自愈（dev 也一样）。

## 副本变慢（`sub_servant_slow.py`）

两个副本，其中一个每 300ms `CLIENT PAUSE 150` 一次；400 个连接各订自己的物品，每秒 200 次插入；按订阅的读
绑在哪个副本上分组。

| 情形 | 读绑健康副本 p50 / p99 | 读绑慢副本 p50 / p99 |
|---|---|---|
| 不暂停（最终） | 106 / 112ms | 107 / 112ms |
| dev | 103 / 521ms | 214 / 517ms |
| 通知全在健康副本（第一版里绑到健康副本的 worker） | 152 / 327ms | 161 / 333ms |
| 通知全在慢副本（第一版里绑到慢副本的 worker） | 250 / 526ms | 246 / 521ms |
| 最终（通知分到两个副本） | 230 / 530ms | 236 / 528ms |

- tick 屏障：一个 tick 里最慢的读决定这批何时交付，读绑在健康副本上的订阅也被拖慢，两组没有区别。
- 分到各副本之后，一半频道的通知本身就经由慢副本送达（暂停期间它的 keyspace 通知也推迟），每个 worker 都吃
  到一部分；第一版是一半 worker 全吃、一半基本不吃，按期望值相当。把 tick 末尾等 SUBSCRIBE 的上限调小
  （`--subscribe-wait`）帮助不大：0.2 个 interval 时 p50 238ms，0 时 191ms。
- dev 读绑健康副本的一半 p50 不受影响，但 p99 一样到 520ms。

## 其他

- `push_encode_cost.py`：服务端 pipeline 编码一帧聊天更新 2.2µs、59 字节（原始 JSON 约 363 字符）。
- 全量 GC 停顿与分支无关：2000 连接时一次约 230ms，堆越大越长；可以考虑启动完成后 `gc.freeze()`、调大
  `gc.set_threshold`，或者减少长期存活的小对象（聊天的行订阅对象是大头，共享订阅后会少很多）。
