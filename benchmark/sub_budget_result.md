# 订阅预算测量结果（sub_budget.py / sub_budget_ws.py）

回答的问题：预估 N 人在线时，每人给多少订阅合适？这和数据更新频率是什么关系？

结论先行：**订阅数本身几乎不要钱，要钱的是"读"和"推"，两种订阅算法不同。**

- **共享订阅**（`EVERYBODY` / `USER` 组件，或 caller 是 admin）：同一查询在一个 worker 内共享一个订阅对象
  （设计稿 `docs/superpowers/specs/2026-09-29-shared-subscriptions-design.md`）。一条通知每个 worker 读、
  比对一次，约 60~90µs，与订了它的连接数无关；每个成员只付推送，一帧约 13~18µs（含 ws 编码发送），同一
  tick 交给一个订阅的多行合成一帧。
- **私有订阅**（`OWNER` / `RLS` 组件的普通玩家）：每个连接各读各比。一次行更新的交付约 80µs，一次行进出
  （要重查索引、增删行频道）约 160~200µs。
- 索引订阅：点查询（`owner=me`、`zone=z`）只在自己那个值有行进出时被叫醒，可以随便用；区间查询会被该索引
  任何值的变动叫醒。
- 预算按"每个 worker 每秒的通知数"和"每秒推的帧数"来定，而不是按"每人几行"。

这一版在 worker 级订阅器、同查询共享、发送循环直接取待发区之后重测（2026-09-29）。之前每个连接各订各读，
按交付数付费（Windows 上 K=10 的 AOI 一次交付约 100µs），那一版见本文件的 git 历史。

## 环境

- Intel Core Ultra X7 358H 笔记本，CachyOS（Linux 7.2），性能模式；Python 3.14.7 + uvloop；Redis 8.10.2
  （docker host 网络，主 / 副本各绑一个核）
- HeTu `perf/shared-subscriptions` @ `14e6592`；订阅进程 / 服务器 worker 绑 P 核 CPU0，写进程在低功耗 E 核，
  ws 客户端在 E 核
- 数字是 CPU 时间。P 核频率随负载在 2~4.5GHz 之间变，低负载那几档的 µs 偏高（最多约 2 倍），下面的成本
  模型按高负载的数字取。跨代码、跨负载比较开销请用 `sub_scenarios_ws.py` 的周期数

## 成本模型

一次写入 → Redis 通知（行和整个索引是 keyspace 事件，表级 / 索引值频道是 commit 主动 PUBLISH）→ 每个 worker 每个副本一条
pubsub 连接收到 → worker 级订阅器按 tick 合批（相邻 tick 至少隔 5ms，同一频道的通知 100ms 内只读一次）→
本 tick 要读的行按表批量读 → 比对 → 交给成员连接的待发区 → 发送循环取走、编码、推送。

| 单位事件 | worker CPU | 副本 CPU | 说明 |
|---|---|---|---|
| **共享订阅**：一条通知的读与比对（每个 worker 一次） | 60~90µs | 20~25µs（约 2.5 条命令） | 与成员数无关；写得越密批量越大，摊得越薄 |
| **共享订阅**：推一帧给一个成员 | 13~18µs（1~3 行的小帧）<br>进程内不含 ws 约 1µs | — | 帧越大越贵（聊天 20 行一帧约 33µs） |
| **私有订阅**：一次行更新的交付（读 + 比对 + 推送） | ~80µs | ~18µs（2.5 条命令） | 背包只改不增删，4000 次/秒 |
| **私有订阅**：一次行进出（重查索引、增删行频道、补读、推送） | 160~200µs | 35~50µs（约 8 条命令） | 背包增删，2000~4000 次/秒 |
| **通知**：被合批吞掉的一条 Redis 消息 | 15~35µs | — | 热点行 100ms 内的多条通知只读一次 |
| **跨区**：一行改了 zone（共享订阅的新旧两个 zone 重查） | 170~370µs | 30~70µs | 与两个 zone 的成员数无关 |
| 静态 | 每连接常驻 7~31KB（进程内、不含 ws 连接本身，AOI 每 zone 100~10 人）；订阅建立 0.3~1.7ms/连接（后加入者不读库） | ~260B /（频道, worker） | 频道按 worker 去重；共享订阅的快照约每行 400B × 每个 worker 一份 |

每个连接的每个订阅一个 tick 最多一帧。同一频道的通知 100ms 内合成一次，所以只订一个热点频道（如聊天的
索引）的连接每秒最多约 10 帧；订了很多行、各行分别在变的（AOI），帧数不超过这些行每秒的变动次数，负载高时
同 tick 到期的合成一帧（实测每帧 1.1~3.4 行）。

## 天花板（本机，1 个 worker）

| 负载 | 实测 | 建议预算（≈60% 核，事件循环还要处理 RPC） |
|---|---|---|
| 共享订阅，小帧推送 | 聊天 2000 连接 × 10 帧/秒：0.34 核；AOI 1000 连接 1.7 万帧/秒 + 2000 通知/秒：0.36 核 | 约 3 万帧/秒，或约 8000 通知/秒，按成本模型折算 |
| 私有订阅，行更新 | 4000 次/秒：0.31 核 | 约 7500 次/秒 |
| 私有订阅，行进出 | 4000 次/秒：0.63 核 | 约 3500 次/秒 |
| 1 个 Redis 副本 | 每个 worker 的每条通知约 20~25µs | 约 2.5 万（worker × 通知）/秒 |
| Redis 连接数 | workers × 副本数（pubsub）+ 读池上限 `max_connections`（默认 64） | 与在线人数无关 |

- 共享订阅的推送是一轮一轮扇出的，一轮占着事件循环，RPC 往返 p99 约等于一轮的时长（聊天 2000 连接时
  20~60ms）。到 0.6~0.7 核后 RPC 的 p50 也开始变差（`sub_scenarios_result.md` 聊天 200 条/秒）。
- 超过预算的表现：同一连接的更新合进更少的帧（交付率下降），写→客户端延迟从约 110ms 涨上去，积压年龄变大；
  超过 `DROP_AFTER`（2 分钟）的通知会被丢弃。

## 预算公式

每个 worker 分别算（W 个 worker 各有自己的共享订阅，同一条通知每个 worker 都读一次）：

```
N_s = 共享订阅每秒收到的通知数（本 worker 上有人订的行 / 索引值的变动次数）
F   = 本 worker 每秒推给各连接的帧数之和
D_u = 私有订阅每秒的行更新交付数        D_m = 私有订阅每秒的行进出数

worker 核 ≈ (N_s × 75µs + F × 17µs + D_u × 80µs + D_m × 180µs) / 1e6 / 0.6
副本核    ≈ Σ_workers (N_s × 25µs + D_u × 20µs + D_m × 45µs) / 1e6 / 0.6
```

- 共享订阅的读随 worker 数翻倍：同一份热门数据，开 W 个 worker 就读 W 次。在线人数多时它仍远小于推送，
  但 worker 开得过多、每个 worker 人又少时，读会变成大头。
- 帧数 F：每个订阅每 tick 最多一帧，热点频道每连接每秒 ≤10 帧；AOI 类不超过它订的行里每秒变动的行数，
  负载高时同 tick 到期的合成一帧。

### 算例

- **AOI，N=1000、每人订自己 zone 的 50 行、每 zone 10 人、每行 1Hz**（100 个 zone，5000 行各 1Hz）：
  1 个 worker：读 N_s = 5000 次/秒（0.38 核）+ 推 F ≈ 1000 × 15 帧/秒（每帧约 3 行，0.26 核）≈ 0.64 核，
  按 60% 预算约 1.1 个核；副本约 0.2 核。旧实现按交付数算约 9 个 worker 核、2 个副本。开 4 个 worker 分摊
  连接：每个仍要读 5000 次/秒（0.38 核），推送分到四份（0.06 核）→ 按预算共约 2.9 核、副本约 0.8 核，这种
  负载少开几个 worker 更划算。
- **同屏 M 人互相可见**（每人都订这 M 行）：共享一个订阅，读 M × F 次/秒，推约 M × min(M × F, 10~15)
  帧/秒。M=100、F=1Hz：读 100 次/秒（7.5ms）+ 约 1500 帧/秒（25ms）≈ 0.03 核；旧实现是 1 万交付/秒
  ≈ 1 个核。
- **背包 `range(Item, owner=me)`**（私有点查询）：别人捡道具不打扰你，自己的物品改一次约 80µs、进出一次约
  180µs。1000 人每人每秒一次 → 0.08~0.18 核。同样的需求写成区间查询（私有），全服拾取 ≥10 次/秒后每个
  在线玩家固定付 ~1.8ms CPU/秒，1000 人就是 1.8 核纯空转。
- **全服聊天**（2000 连接各订最近 1024 条）：见 `sub_scenarios_result.md`，1 个 worker 10 条/秒约 0.34 核，
  约 200 条/秒到顶（100 条/秒以内 RPC 往返的 p50 不受影响）。
- **AOI 跨区**：一次跨区只让新旧两个 zone 的共享订阅各重查一次（170~370µs），与 zone 里的人数无关。

  约 1µs。
- 副本 CPU 也只跟通知走：每条 20~27µs，K=1、10、100 都一样。
- 交付率随写入量下降是合批：同一行 100ms 内写两次只推最新的一次。
- 热点行：1807 条通知/秒只读了约 200 次，扣掉读，每条被吞掉的通知约 30µs（这档只有 0.08 核，频率低，
  满频时约一半）。
- 跨区：move10 比 K10_W300 多 0.011 核（每次跨区约 370µs），move50 多 0.025 核（约 170µs，批量更大）。

  Redis 侧每 (频道, worker) 约 260B；Redis 连接数 6~7（pubsub + 读池 + 写进程），与连接数无关。

## 注意事项

1. 区间查询仍是整索引广播：共享的区间订阅每个 worker 每个查询最多 ~10 次重查/秒，与订阅者数无关；私有
   （RLS）的区间订阅按订阅者付，热索引上每个订阅者约 1.8ms CPU/秒。高频跨区的私有区间 AOI 要么改点查询，
   要么按地图 / 区拆组件缩小订阅者数。
2. 点查询的值频道由 commit 发出，老版本的写入方（老 worker、老 headless 进程）不发，混跑时新 worker 上的点
   订阅会漏通知，写入方要一起升级；`maint.py` 的离线维护路径不发表级 / 值频道通知。
3. Windows 下 Sanic 强制 `WindowsSelectorEventLoopPolicy`，`select()` 上限 512 fd，单 worker 约 150~200 个
   连接就崩（"too many file descriptors in select()"）。Linux 无此问题。
4. Redis 副本单线程。共享订阅的读按 worker 数乘，多副本靠 `servants` 分摊：通知按频道分到各副本订阅，读随机
   选副本。写入侧 master 每 commit 会多发每个索引字段一条值频道 PUBLISH，无订阅者时是一次 dict 查找。
5. 2000 连接的 worker 全量 GC 一次约 100~240ms（每连接约 285 个被追踪的对象，私有行订阅每行约 4 个），见
   `docs/superpowers/specs/2026-09-29-push-path-and-gc-design.md` §4。

## 复现

```bash
# 专用 Redis（会 FLUSHALL），host 网络，副本带 keyspace 通知配置
docker run -d --name hetu-bench-master --network host --cpuset-cpus 2 redis:latest \
    redis-server --port 23400 --save "" --appendonly no
docker run -d --name hetu-bench-replica --network host --cpuset-cpus 3 redis:latest \
    redis-server --port 23401 --save "" --appendonly no --replicaof 127.0.0.1 23400 \
    --notify-keyspace-events ghzK

cd benchmark
P="--limit 50 --duration 20 --sub-cpus 0 --writer-cpus 12,13,14,15 --writers 4 --writer-coroutines 16"
uv run python sub_budget.py --conns 200 --zones 200 --writes 1000 $P   # K=1
uv run python sub_budget.py --conns 200 --zones 20 --writes 1000 $P    # K=10
uv run python sub_budget.py --conns 1000 --zones 10 --writes 1000 $P   # K=100
uv run python sub_budget.py --conns 200 --zones 20 --writes 2000 --hot-rows 20 $P
uv run python sub_budget.py --conns 200 --zones 20 --writes 300 --move-ratio 0.1 $P
uv run python sub_budget_ws.py --conns 1000 --zones 100 --writes 1000 --limit 50 --duration 20 \
    --server-cpus 0 --client-cpus 4,5,6,7,8,9,10,11 --client-procs 8 --writer-cpus 12,13,14,15 \
    --writers 4 --writer-coroutines 16
```

CPU 编号按 Intel 混合架构笔记本（P 核 0-3、E 核 4-11、低功耗 E 核 12-15），别的机器按实际调整；
不给 `--*-cpus` 就不绑核。Linux 上可以用 `sub_budget_ws.py --workers N` 直接测多 worker。
